## 1. What FastAPI Is & Why It's Fast

**FastAPI** is a modern Python web framework for building APIs, built on top of **Starlette** (the underlying ASGI toolkit, handling routing/requests/responses/WebSockets) and **Pydantic** (data validation/serialization via Python type hints).

**Why it's fast (commonly asked to justify the name/reputation):**
- **ASGI-based** (Section 2), enabling genuine async I/O — can handle many concurrent I/O-bound requests (DB calls, external API calls) far more efficiently than a synchronous WSGI framework under similar load, since it doesn't need to block a whole worker thread/process per in-flight request (ties directly to the Python guide's `asyncio` section).
- **Starlette** provides a lean, high-performance routing/ASGI layer (benchmark-competitive with Node.js/Go frameworks for I/O-bound workloads) rather than FastAPI reinventing low-level HTTP handling itself.
- **Pydantic v2** (current major version) is implemented with a **Rust-based core** (`pydantic-core`), making validation/serialization dramatically faster than the pure-Python validation typical of older frameworks.

**FastAPI's core value proposition beyond raw speed (commonly asked "why FastAPI over Flask/Django"):**
- **Type-hint-driven validation and serialization**: function parameter type hints automatically become request validation rules, and Pydantic models automatically become both request-body parsers and response serializers — eliminating a large class of manual parsing/validation boilerplate common in other frameworks.
- **Automatic interactive API documentation** (Section 14) generated directly from the code (type hints + docstrings), with zero extra effort — a direct, practical application of the OpenAPI/Swagger concepts from the APIs & HTTP guide (Section 22 there).
- **Native async support** as a first-class citizen, not bolted on.

## 2. ASGI vs WSGI

*(Builds directly on the Python guide's `asyncio` section and the general HTTP/WebSockets material from the APIs & HTTP and Networking guides.)*

**WSGI (Web Server Gateway Interface)** — the traditional, **synchronous** Python web server interface (used by Flask, Django's classic mode, older frameworks): each incoming request is handled by blocking a worker (thread or process) for the request's **entire** duration, including any I/O waits (DB queries, external API calls) — concurrency is achieved only by running **multiple** worker processes/threads in parallel (ties to the OS guide's thread-pool discussion).

**ASGI (Asynchronous Server Gateway Interface)** — the modern **asynchronous** successor, supporting `async`/`await`-based request handling (and, critically, **WebSockets** and **long-lived connections**, which WSGI's synchronous, one-request-per-worker-slot model handles poorly). A single ASGI worker can handle **many concurrent** in-flight requests, since an `await`-ing request handler yields control back to the event loop during I/O waits (exactly the mechanism described in the Python guide's `asyncio` section) rather than blocking an entire worker.

**WSGI vs ASGI (a very commonly asked comparison table):**
| | WSGI | ASGI |
|---|---|---|
| Concurrency model | One worker blocked per in-flight request | Single event loop handles many concurrent requests via `async`/`await` |
| WebSocket support | Not natively supported (requires workarounds) | Native, first-class support |
| Best for | CPU-bound or simple synchronous workloads | I/O-bound workloads with high concurrency (many simultaneous slow DB/API calls, real-time features) |
| Common servers | Gunicorn (with sync workers), uWSGI | Uvicorn, Hypercorn, Daphne |
| Example frameworks | Flask, Django (classic) | FastAPI, Starlette, Django (ASGI mode, 3.0+) |

**Interview trap:** *"Does ASGI make FastAPI automatically fast for everything?"* No — ASGI's concurrency benefit is specifically for **I/O-bound** workloads (many requests waiting on network/DB calls); genuinely **CPU-bound** work (heavy computation) still blocks the single event loop thread just as it would in any single-threaded async system (directly parallels the Python guide's GIL/`asyncio` discussion) — CPU-bound work in a FastAPI app should be offloaded to a background worker/process pool (e.g., via `run_in_executor`, Celery, or a separate `multiprocessing`-based service) rather than run directly in an `async def` handler.

## 3. Path Operations & Routing

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/items/{item_id}")
async def read_item(item_id: int):
    return {"item_id": item_id}

@app.post("/items/")
async def create_item(item: dict):
    return item
```

**Path operation decorators** (`@app.get`, `.post`, `.put`, `.patch`, `.delete`, etc.) map directly onto the HTTP methods covered in the APIs & HTTP guide (Section 5 there) — FastAPI is explicitly designed around REST semantics, with each decorator corresponding to the appropriate HTTP verb's conventional meaning (safe/idempotent GET, non-idempotent POST for creation, etc.).

**Route ordering matters (a commonly tested gotcha):** FastAPI matches routes in the **order they're declared** — a more specific static route must be declared **before** a more general dynamic (path-parameter) route that could also match the same URL pattern, or the dynamic route will greedily intercept requests intended for the static one.
```python
@app.get("/users/me")       # MUST come first
async def get_current_user(): ...

@app.get("/users/{user_id}") # otherwise, a request to /users/me would match HERE instead,
async def get_user(user_id: str): ...  # with user_id="me" — likely not the intended behavior
```

**`APIRouter`**: Allows splitting routes across multiple files/modules (grouped by resource/feature area) and later including them into the main app — analogous to Java Spring's controller-per-resource organization, or Express.js's router modules — a standard pattern for structuring any non-trivial FastAPI application.
```python
router = APIRouter(prefix="/items", tags=["items"])

@router.get("/")
async def list_items(): ...

app.include_router(router)
```

## 4. Path, Query, and Body Parameters

FastAPI infers **where** a parameter comes from based on its declaration context and type — a core mechanic worth understanding precisely.

```python
from fastapi import Query, Path, Body
from pydantic import BaseModel

class Item(BaseModel):
    name: str
    price: float

@app.put("/items/{item_id}")
async def update_item(
    item_id: int = Path(..., description="The ID of the item", gt=0),   # PATH parameter — declared in the URL pattern, so it's a path param
    q: str | None = Query(None, max_length=50),                          # QUERY parameter — a simple type NOT in the path, becomes a query param
    item: Item = Body(...)                                                # BODY parameter — a Pydantic model, parsed from the JSON request body
):
    return {"item_id": item_id, "q": q, "item": item}
```

**The inference rule (commonly asked to state precisely):**
- If the parameter name appears in the **path pattern** (`{item_id}`), it's a **path parameter**.
- If it's a **simple type** (`str`, `int`, `bool`, etc.) and **not** in the path, it's assumed to be a **query parameter**.
- If it's declared as a **Pydantic model** (or explicitly marked with `Body(...)`), it's parsed from the **request body**.

**Validation via `Query`/`Path`/`Body` (ties directly to the APIs & HTTP guide's general validation concerns):** These helper functions let you attach validation constraints (`gt`, `ge`, `lt`, `le`, `min_length`, `max_length`, `regex`) and metadata (used in the auto-generated docs, Section 14) directly in the function signature — validation failures automatically produce a structured `422 Unprocessable Entity` response (ties to the APIs & HTTP guide's status code discussion) without any manual validation code needed.

## 5. Pydantic Models & Validation

**Pydantic** is the data-validation library FastAPI is built around — models are defined using standard Python type hints (`BaseModel` subclasses), and validation happens automatically at runtime when data is parsed into (or serialized out of) those models.

```python
from pydantic import BaseModel, Field, EmailStr, field_validator

class UserCreate(BaseModel):
    username: str = Field(..., min_length=3, max_length=20)
    email: EmailStr                    # built-in email format validation
    age: int = Field(..., gt=0, le=120)
    tags: list[str] = []                # default value — becomes optional

    @field_validator("username")
    @classmethod
    def username_alphanumeric(cls, v):
        if not v.isalnum():
            raise ValueError("must be alphanumeric")
        return v
```

**Why this matters practically (commonly asked to articulate the benefit over manual validation):** A request body that fails validation (missing required field, wrong type, failing a `Field` constraint, or a custom `field_validator`) never even reaches your endpoint function's body — FastAPI intercepts it and automatically returns a `422` response with a detailed, structured error explaining exactly what failed and where — eliminating a large class of manual `if`/`raise` boilerplate that would otherwise clutter every endpoint.

**Pydantic v1 vs v2 (worth knowing the terminology shift, since it's a commonly referenced recent breaking change):** Pydantic v2 (a ground-up rewrite with the Rust-based core mentioned in Section 1) renamed several APIs — `@validator` → `@field_validator`, `.dict()` → `.model_dump()`, `.json()` → `.model_dump_json()`, and config moved from an inner `class Config` to `model_config = ConfigDict(...)`. Modern FastAPI codebases (and interview expectations) generally assume v2.

**Nested models & type composition (commonly asked to demonstrate):**
```python
class Address(BaseModel):
    city: str
    zip_code: str

class User(BaseModel):
    name: str
    address: Address            # nested model — validated recursively
    previous_addresses: list[Address] = []
```

**`Optional`/`| None` and default values (commonly asked distinction):** A field with a default value (`tags: list[str] = []`) is **optional** in the request; a field with **no** default (`username: str`) is **required** — annotating a type as `Optional`/`| None` alone, without a default, still makes the field **required** but allows `None` as a valid value — a commonly tested subtlety (required-but-nullable vs genuinely optional are two different, sometimes conflated concepts).

## 6. Response Models & Status Codes

```python
from fastapi import status

class UserOut(BaseModel):
    username: str
    email: str
    # password is deliberately excluded — this model defines the PUBLIC shape

@app.post("/users/", response_model=UserOut, status_code=status.HTTP_201_CREATED)
async def create_user(user: UserCreate):
    saved_user = save_to_db(user)  # saved_user might internally include a hashed_password field
    return saved_user               # FastAPI automatically filters the response down to UserOut's fields only
```

**Why `response_model` matters (a very commonly asked security/design question):** It defines the **public-facing contract** for a response, independent of whatever internal object/dict is actually returned from the function — FastAPI automatically **filters out** any fields not declared on the response model (e.g., ensuring a hashed password or internal-only field never accidentally leaks in an API response, even if the returned object happens to contain it) — a meaningful, automatic security/encapsulation benefit, not just a documentation nicety.

**`response_model_exclude_unset`/`exclude_none`**: Additional response-model options for omitting fields that weren't explicitly set (useful for PATCH-style partial-update responses) or that are `None` — worth knowing exist for fine-tuning serialized output shape.

**Status codes**: FastAPI's `status` module provides named constants for all standard HTTP status codes (`status.HTTP_404_NOT_FOUND`, etc.) — ties directly to the APIs & HTTP guide's Section 6, with FastAPI simply providing ergonomic, typo-resistant access to the same standard codes.

## 7. Dependency Injection

FastAPI's **`Depends()`** system is one of its most distinctive features — a declarative way to share reusable logic (DB sessions, auth checks, pagination parameters, common query logic) across multiple path operations, with FastAPI handling the actual invocation and value-passing automatically.

```python
from fastapi import Depends

def get_db():
    db = SessionLocal()
    try:
        yield db          # everything before yield = setup; everything after = teardown (mirrors a context manager)
    finally:
        db.close()

def get_current_user(token: str = Depends(oauth2_scheme), db: Session = Depends(get_db)):
    user = decode_token_and_fetch_user(token, db)
    if not user:
        raise HTTPException(status_code=401, detail="Invalid credentials")
    return user

@app.get("/profile")
async def read_profile(current_user: User = Depends(get_current_user)):
    return current_user
```

**How it works (commonly asked to explain the mechanism):** `Depends(some_function)` tells FastAPI to **call `some_function`** (resolving its own dependencies recursively first, if it has any — dependencies can be nested/chained arbitrarily deep) before running the actual path operation function, and to **inject its return value** as the corresponding parameter — a form of the Dependency Inversion / Dependency Injection principle from the OOP guide's SOLID section, applied at the framework level.

**Generator-based dependencies (the `yield` pattern shown above, commonly asked to explain):** A dependency function using `yield` instead of `return` behaves like a **context manager** (directly parallels the Python guide's Section 17) — code before `yield` runs as setup (e.g., opening a DB session), the yielded value is injected into the endpoint, and code after `yield` (typically in a `finally` block) runs as teardown **after the request completes** (even if an exception occurred) — this is the standard, idiomatic FastAPI pattern for managing per-request resources like database sessions.

**Dependency caching within a single request (a commonly tested subtlety):** By default, FastAPI **caches** a dependency's result within the scope of a single request — if multiple parts of the dependency graph (e.g., two different endpoint dependencies) both depend on `get_db`, it's only actually **called once** per request, and the same session object is shared/reused — avoiding redundant work; this can be disabled per-dependency with `Depends(fn, use_cache=False)` if fresh evaluation is genuinely needed.

**Class-based dependencies:** A callable class (implementing `__call__`) can also be used with `Depends()`, useful for dependencies needing their own configuration/state (e.g., a pagination dependency parameterized by default page size) — a direct application of the general callable-object concept.

## 8. `async def` vs `def` Path Operations

A frequently asked, genuinely important FastAPI-specific performance question, directly building on the Python guide's `asyncio`/GIL discussion.

**`async def` path operations**: Run directly on the main event loop. **Must not** contain any **blocking, synchronous** I/O calls (a synchronous DB driver call, `time.sleep()`, a blocking `requests.get()`) — doing so blocks the **entire event loop**, stalling every other concurrent request being handled by that worker process, since there's only one thread running the loop.

```python
# BAD — blocks the entire event loop for every other concurrent request during this call
@app.get("/bad")
async def bad_endpoint():
    time.sleep(5)          # SYNCHRONOUS blocking call inside an async function — defeats the purpose entirely
    return {"status": "done"}

# GOOD — properly async, yields control during the wait
@app.get("/good")
async def good_endpoint():
    await asyncio.sleep(5)  # ASYNCHRONOUS — yields control back to the event loop during the wait
    return {"status": "done"}
```

**Plain `def` path operations**: FastAPI automatically runs these in a **separate thread pool** (via Starlette's `run_in_threadpool`, itself using `asyncio`'s `run_in_executor`) — so a synchronous, blocking call inside a plain `def` endpoint does **not** block the main event loop; it just occupies one thread from the pool while other requests continue being served on the event loop (or other threadpool threads).

**The practical decision rule (very commonly asked to state clearly):**
- Use **`async def`** when your endpoint's I/O is genuinely `await`-able (an async DB driver, `httpx`'s async client, `asyncio`-native operations) — this is the most efficient path, since it never occupies a whole OS thread just to wait.
- Use plain **`def`** when your endpoint calls **synchronous/blocking** libraries (e.g., a legacy sync DB driver, a CPU-bound computation, a blocking third-party SDK) — letting FastAPI's threadpool absorb the blocking without stalling the event loop.
- **Never** put blocking synchronous calls inside `async def` — this is one of the single most common, most performance-damaging mistakes in real-world FastAPI code, and a very frequently asked "spot the bug" interview question.

**Interview trap:** *"Is `async def` always faster than plain `def`?"* No — it's only faster/beneficial when the endpoint's work is I/O-bound **and** uses genuinely async-compatible libraries throughout; an `async def` endpoint that calls a blocking library is actually **worse** than a plain `def` endpoint doing the same blocking call, since the plain `def` version at least gets automatically offloaded to a thread pool, while the `async def` version blocks the shared event loop directly, stalling all other concurrent requests.

## 9. Middleware

Functions that run for **every** request/response, wrapping the actual path operation — used for cross-cutting concerns (logging, timing, CORS, authentication headers) — ties directly to the reverse-proxy/middleware-pipeline concept from the Networking guide's Chain of Responsibility discussion.

```python
import time
from starlette.middleware.base import BaseHTTPMiddleware

@app.middleware("http")
async def add_process_time_header(request: Request, call_next):
    start_time = time.time()
    response = await call_next(request)  # calls the NEXT middleware/the actual path operation
    response.headers["X-Process-Time"] = str(time.time() - start_time)
    return response
```

**`CORSMiddleware` (a very commonly used built-in, ties directly to the APIs & HTTP guide's CORS section and the Security guide's CORS section):**
```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://example.com"],  # never use "*" combined with allow_credentials=True (Security guide, Section 10)
    allow_credentials=True,
    allow_methods=["GET", "POST"],
    allow_headers=["*"],
)
```

**Middleware execution order (a commonly tested detail):** Middleware added later wraps **around** middleware added earlier — requests flow through middleware in the **reverse** order they were added (last-added runs first on the way in), and responses flow back through in the **original** added order — the same nested "onion layer" execution model as the Chain of Responsibility / middleware-pipeline pattern discussed in the Networking guide.

**Middleware vs Dependencies (a commonly asked distinction, since both can intercept requests):** Middleware runs for **every** request to the app, has no access to path-specific data (route parameters aren't resolved yet at the middleware layer) or dependency injection, and operates at the raw request/response level. Dependencies (Section 7) are attached to **specific** path operations (or routers), have full access to resolved path/query/body parameters, and integrate with the dependency-injection graph (including automatic documentation) — middleware for broad, uniform cross-cutting concerns; dependencies for endpoint-specific or route-group-specific reusable logic.

## 10. Background Tasks

For work that should happen **after** a response has already been sent to the client, without making the client wait for it.

```python
from fastapi import BackgroundTasks

def send_email_notification(email: str, message: str):
    # potentially slow — sending an actual email
    time.sleep(2)
    print(f"Email sent to {email}: {message}")

@app.post("/register")
async def register_user(email: str, background_tasks: BackgroundTasks):
    background_tasks.add_task(send_email_notification, email, "Welcome!")
    return {"message": "Registered"}  # response returns IMMEDIATELY — the email sends afterward, in the background
```

**How it works (commonly asked to explain, and to distinguish from a "true" task queue):** The background task runs **within the same process**, after the response has been sent, using the same event loop (or thread pool, for sync task functions) — it is **not** a separate worker process or distributed task queue; if the server process crashes or restarts before the background task completes, the task is simply **lost**, with no persistence or retry mechanism.

**`BackgroundTasks` vs a real task queue (Celery, RQ, Arq) — a very commonly asked "when would you need more than this" question:** `BackgroundTasks` is appropriate for **lightweight, fire-and-forget** work that's acceptable to lose on a crash (e.g., sending a non-critical notification, writing a log entry, invalidating a cache). For work that **must** be reliably completed (payment processing follow-ups, critical email delivery, anything needing retries/persistence/scheduling/distribution across multiple worker machines), a dedicated task queue (Celery + a broker like Redis/RabbitMQ) is the correct tool — `BackgroundTasks` explicitly does **not** provide durability guarantees.

## 11. Authentication & Security

*(Builds directly on the APIs & HTTP guide's OAuth2/JWT sections and the Security guide's Authentication section.)*

**`OAuth2PasswordBearer` (FastAPI's built-in helper for the common "bearer token in the Authorization header" pattern):**
```python
from fastapi.security import OAuth2PasswordBearer

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token")  # tells FastAPI's docs UI where to POST for a token

@app.get("/protected")
async def protected_route(token: str = Depends(oauth2_scheme)):
    # token is automatically extracted from the "Authorization: Bearer <token>" header
    user = verify_and_decode_jwt(token)
    return user
```
This is a thin FastAPI-specific wrapper — it handles **extracting** the bearer token from the request and integrates with the auto-generated docs' "Authorize" button; it does **not** itself verify/decode the JWT — that verification logic (typically using a library like `python-jose` or `PyJWT`) must be implemented explicitly, exactly per the JWT mechanics covered in the APIs & HTTP guide (Section 10 there).

**Password hashing (ties directly to the Security guide's Section 4):** FastAPI has no built-in password hashing — the standard practice is using `passlib` (with `bcrypt`) or Python's own hashing libraries, following the exact same salting + slow-algorithm principles discussed there; never store or compare plaintext passwords.

**Security as a dependency (the idiomatic FastAPI pattern, reinforcing Section 7):** Authentication/authorization checks are implemented as ordinary **dependencies** (like `get_current_user` shown in Section 7) — this means auth logic is declared once and reused declaratively across any endpoint simply by adding it as a `Depends()` parameter, rather than manually checking headers in every function body, and it automatically integrates with the auto-generated OpenAPI docs' security scheme metadata.

## 12. Error Handling

```python
from fastapi import HTTPException

@app.get("/items/{item_id}")
async def read_item(item_id: int):
    item = db.get(item_id)
    if not item:
        raise HTTPException(status_code=404, detail="Item not found")
    return item
```

**`HTTPException`**: The standard way to return a specific error status code + message from within a path operation — FastAPI catches it and converts it into the appropriate JSON error response automatically.

**Custom exception handlers (for consistent, app-wide error formatting, or for translating domain-specific exceptions):**
```python
class ItemNotFoundError(Exception):
    def __init__(self, item_id: int):
        self.item_id = item_id

@app.exception_handler(ItemNotFoundError)
async def item_not_found_handler(request: Request, exc: ItemNotFoundError):
    return JSONResponse(
        status_code=404,
        content={"message": f"Item {exc.item_id} not found"},
    )
```
This lets business/domain logic raise **meaningful, domain-specific exceptions** (ties directly to the OOP guide's custom-exception best practices) without those layers needing to know anything about HTTP status codes at all — the exception handler is the single place that translates domain errors into the appropriate HTTP response, a clean separation of concerns.

**Validation error responses (automatic, from Pydantic — Section 5):** FastAPI automatically catches Pydantic's `ValidationError` for request parsing failures and returns a structured `422` response with per-field error details — this default behavior can be overridden with a custom handler for `RequestValidationError` if a different error response shape is needed for API consistency.

## 13. Database Integration & Async ORMs

*(Ties directly to the Databases guide, and Section 8's `async def`/`def` discussion above — the choice of ORM/driver directly determines which pattern is correct.)*

**Synchronous ORMs (e.g., classic SQLAlchemy with a sync driver like `psycopg2`)**: Must be used in **plain `def`** path operations (or explicitly offloaded), since their DB calls block — using them inside `async def` would block the entire event loop, exactly the mistake described in Section 8.

**Async ORMs/drivers (e.g., SQLAlchemy 2.0's async mode with `asyncpg`, `Tortoise ORM`, `SQLModel` with async sessions, `databases` library)**: Designed to be `await`-ed directly inside `async def` endpoints, integrating properly with the event loop without blocking it.

```python
# Async SQLAlchemy pattern (SQLAlchemy 2.0+)
async def get_db():
    async with AsyncSessionLocal() as session:
        yield session

@app.get("/items/{item_id}")
async def read_item(item_id: int, db: AsyncSession = Depends(get_db)):
    result = await db.execute(select(Item).where(Item.id == item_id))
    item = result.scalar_one_or_none()
    if not item:
        raise HTTPException(404, "Not found")
    return item
```

**Connection pooling (ties directly to the Databases guide's general connection-management concerns):** Both sync and async setups typically use a **connection pool** (managed by the ORM/driver, or a library like `asyncpg`'s built-in pool) rather than opening a fresh DB connection per request — the `get_db` dependency pattern (Section 7) is specifically designed to **borrow** a connection/session from the pool for the duration of one request and return it afterward, not to manage raw connections directly.

**`SQLModel`** (from the same author as FastAPI): Combines Pydantic and SQLAlchemy into a single model definition — the same class can serve as both the Pydantic request/response schema **and** the SQLAlchemy ORM table definition, reducing duplication between "API schema" and "database schema" classes that's common when using separate Pydantic and SQLAlchemy models side by side.

## 14. Automatic Docs (OpenAPI/Swagger)

*(Directly ties to the APIs & HTTP guide's Section 22 — FastAPI is essentially a live demonstration of that section's benefits.)*

FastAPI automatically generates a complete **OpenAPI schema** from your route definitions, Pydantic models, and type hints — with **zero** additional annotation effort beyond writing idiomatic, type-hinted code — served at `/openapi.json` by default, and rendered as interactive documentation at `/docs` (**Swagger UI**) and `/redoc` (**ReDoc**, an alternative documentation renderer).

**What gets automatically documented (commonly asked to enumerate):** Path/query/body parameters (including types, whether required, and validation constraints from `Field`/`Query`/`Path`), request/response body schemas (from Pydantic models, Section 5-6), possible response status codes (if explicitly declared via `responses={...}` on the decorator), and authentication requirements (from security dependencies, Section 11) — Swagger UI's `/docs` page even includes a live "Try it out" feature to execute real requests directly from the browser, and an "Authorize" button that integrates with `OAuth2PasswordBearer`-style dependencies.

**Enriching the docs (commonly asked to demonstrate):**
```python
@app.get(
    "/items/{item_id}",
    summary="Get an item",
    description="Retrieve a single item by its unique ID.",
    response_description="The requested item",
    responses={404: {"description": "Item not found"}},
)
async def read_item(item_id: int):
    ...
```

**Interview trap:** *"Do you need a separate tool like a Postman collection or manually maintained API docs with FastAPI?"* Not typically for basic API reference documentation — since the docs are generated directly from the live code (types, models, docstrings), they're **guaranteed to stay in sync** with the actual implementation, solving the classic "docs drift out of date from the code" problem that plagues manually maintained API documentation in most other stacks.

## 15. Testing FastAPI Apps

```python
from fastapi.testclient import TestClient

client = TestClient(app)

def test_read_item():
    response = client.get("/items/1")
    assert response.status_code == 200
    assert response.json() == {"item_id": 1}
```

**`TestClient`**: Built on `httpx`, allows making synchronous-looking requests directly against the FastAPI app **in-process** (no actual network socket/running server needed) — fast, simple to write, works even for testing `async def` endpoints (the client itself handles running the app's event loop internally for the duration of each test call).

**Overriding dependencies for testing (a very commonly asked, practically important pattern):** FastAPI provides `app.dependency_overrides` to **replace** a real dependency (e.g., `get_db`, which connects to a real database) with a **test double** (e.g., a function returning a test/in-memory database session) — without touching the actual application code at all, keeping tests fast/isolated and avoiding hitting a real database or external service during unit tests.
```python
def override_get_db():
    yield TestSessionLocal()  # a separate, test-only database session

app.dependency_overrides[get_db] = override_get_db

def test_create_item():
    response = client.post("/items/", json={"name": "Widget", "price": 9.99})
    assert response.status_code == 201
```
This is a direct, practical application of the **Dependency Inversion Principle** from the OOP guide's SOLID section — because endpoints depend on an *abstraction* (whatever `Depends(get_db)` resolves to) rather than a concrete, hardcoded database connection, swapping in a test implementation requires no changes to the endpoint code itself.

## 16. WebSockets in FastAPI

*(Ties directly to the APIs & HTTP guide's WebSockets section and the Networking guide's coverage — FastAPI/Starlette's ASGI foundation, Section 2, is precisely what enables this native support, unlike WSGI-based frameworks.)*

```python
from fastapi import WebSocket

@app.websocket("/ws")
async def websocket_endpoint(websocket: WebSocket):
    await websocket.accept()
    try:
        while True:
            data = await websocket.receive_text()
            await websocket.send_text(f"Echo: {data}")
    except WebSocketDisconnect:
        print("Client disconnected")
```

**Why ASGI matters here (reinforcing Section 2):** A WebSocket connection is inherently **long-lived** — WSGI's synchronous, one-request-blocks-one-worker model handles this extremely poorly (a WebSocket connection would tie up an entire worker for its whole lifetime, severely limiting the number of concurrent connections a server could support); ASGI's event-loop-based model allows a single process to comfortably hold many thousands of concurrent WebSocket connections open simultaneously, since each connection only actively consumes resources while genuinely doing something (sending/receiving), not merely while idly connected.

## 17. Deployment (Uvicorn, Gunicorn, Workers)

**Uvicorn**: The ASGI server that actually runs a FastAPI application (analogous to how a WSGI app needs a server like Gunicorn to actually run it) — implements the low-level HTTP/WebSocket protocol handling and the event loop that FastAPI's `async def` handlers run on.
```bash
uvicorn main:app --host 0.0.0.0 --port 8000
```

**Production deployment — Gunicorn managing multiple Uvicorn workers (a very commonly asked "how would you deploy this" question):**
```bash
gunicorn main:app -w 4 -k uvicorn.workers.UvicornWorker
```
**Why multiple workers, given ASGI's concurrency benefits (a commonly asked "isn't one event loop enough" follow-up):** A single Uvicorn/event-loop process is still fundamentally **one Python process**, constrained by the GIL (Python guide, Section 1) for any CPU-bound portions of work, and represents a single point of failure — running multiple **worker processes** (each with its own independent event loop, and its own GIL) lets the application utilize **multiple CPU cores** in parallel (true process-level parallelism, exactly the `multiprocessing` rationale from the Python guide) and provides resilience (one worker crashing doesn't take down the entire application, and Gunicorn can automatically restart a crashed worker).

**Health checks & graceful shutdown (worth mentioning for a complete deployment answer, ties to the Networking guide's load-balancer health-check discussion):** Production deployments typically expose a lightweight `/health` endpoint for load balancers to poll, and rely on ASGI lifespan events (`@app.on_event("startup")`/`"shutdown"`, or the newer `lifespan` context-manager parameter) to properly initialize/tear down resources like DB connection pools cleanly on deploy/restart, avoiding dropped in-flight requests during rolling deployments.

## 18. Rapid-Fire Interview Q&A

**Q: What's the fundamental difference between ASGI and WSGI, and why does it matter for FastAPI?**
WSGI blocks one worker per in-flight request (synchronous only); ASGI supports async request handling and native WebSockets, letting a single process handle many concurrent I/O-bound requests efficiently — the foundation of FastAPI's async performance story.

**Q: When should you use `async def` vs plain `def` for a path operation?**
`async def` when all I/O in the endpoint is genuinely awaitable (async DB drivers, `httpx`); plain `def` when calling blocking/synchronous libraries, since FastAPI automatically offloads those to a thread pool instead of blocking the shared event loop.

**Q: What does `Depends()` actually do?**
Declares a reusable dependency function FastAPI will call (resolving its own nested dependencies first) before the path operation runs, injecting its return value as a parameter — results are cached per-request by default, and generator-based dependencies (`yield`) get context-manager-style setup/teardown semantics.

**Q: Why is `response_model` valuable beyond documentation?**
It automatically filters the actual returned object down to only the declared fields, preventing accidental leakage of sensitive/internal data (like a hashed password) that might exist on the underlying object but shouldn't be exposed in the API response.

**Q: What's the risk of using `BackgroundTasks` for critical work like payment processing?**
Background tasks run in-process with no persistence — if the server crashes or restarts before the task completes, the work is silently lost, with no retry mechanism; critical/reliable work needs a real task queue (Celery, RQ) instead.

**Q: Why does FastAPI's auto-generated documentation stay accurate over time, unlike many hand-written API docs?**
It's generated directly from the live code (type hints, Pydantic models, decorators) rather than maintained as a separate artifact — any change to the actual implementation is automatically reflected in the docs, eliminating the classic docs-vs-code drift problem.

**Q: Why run multiple Gunicorn-managed Uvicorn workers instead of just one, given ASGI's concurrency model?**
A single process is still bound by the GIL for CPU-bound work and represents a single point of failure; multiple worker processes achieve true multi-core parallelism and resilience (one crashing doesn't take down the whole app), complementing (not replacing) ASGI's per-process I/O concurrency benefit.
